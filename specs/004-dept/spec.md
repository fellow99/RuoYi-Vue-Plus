# 部门管理功能规格 (spec.md)

> 模块：004-dept | 状态：已实现 | 最后更新：2026-08-10

## 1. 模块概述

### 1.1 目的
部门管理模块负责维护系统的组织架构树，支持公司、部门、小组等多层级结构的 CRUD 操作。部门是数据权限体系的基础——角色的数据范围（本部门、本部门及以下）依赖部门树结构进行计算。

### 1.2 解决的问题
- 系统需要一个树形结构来反映真实的组织架构（公司 → 部门 → 小组）
- 数据权限过滤需要基于部门树来判定用户能查看哪些数据
- 部门信息（名称、负责人、联系方式等）需要在系统中统一管理和展示

### 1.3 范围
- ✅ 部门树形结构 CRUD（新增子部门、编辑、删除）
- ✅ 部门排序（orderNum）
- ✅ 部门状态管理（正常/停用）
- ✅ 部门信息：名称、类别编码、负责人、联系电话、邮箱
- ✅ 祖级列表（ancestors）自动维护，支持 find_in_set 查询子部门
- ✅ 部门数据权限过滤（@DataPermission 按 dept_id 过滤）
- ✅ 排除节点的部门列表查询（编辑时避免选择自己或子部门为上级）
- ✅ 删除前置校验：不允许删除默认部门、有子部门、有用户、有岗位的部门
- ✅ 停用前置校验：不允许停用有未停用子部门或有已分配用户的部门
- ❌ 部门本身没有审批流程
- ❌ 部门没有单独的导入导出功能

## 2. 用户故事
- 作为**管理员**，我可以创建公司级部门和子部门，构建企业的组织架构树
- 作为**管理员**，我可以编辑部门信息（名称、负责人、电话等），以确保组织信息准确
- 作为**管理员**，我可以调整部门排序，使部门列表按业务逻辑排列
- 作为**管理员**，我可以在编辑部门时排除自身及子部门作为上级部门，避免形成环路
- 作为**数据权限体系**，我需要通过部门树和祖级字段（ancestors）快速计算角色的数据范围

## 3. 功能需求

- FR-004-001: 系统 MUST 支持查询部门列表（非树形，用于列表展示和导出场景）
- FR-004-002: 系统 MUST 支持查询部门树结构（用于下拉选择、数据权限配置）
- FR-004-003: 系统 MUST 支持查询部门树结构时排除指定节点及其子节点
- FR-004-004: 系统 MUST 支持新增部门，必填项包括父部门ID、部门名称、显示顺序
- FR-004-005: 系统 MUST 在新增部门时自动设置祖级列表（ancestors = 父部门.ancestors + "," + 父部门.deptId）
- FR-004-006: 系统 MUST 支持修改部门信息（名称、类别编码、负责人、电话、邮箱、排序、状态）
- FR-004-007: 系统 MUST 在修改部门时，如果上级部门变更，自动刷新本部门及所有子部门的祖级列表
- FR-004-008: 系统 MUST 在修改部门时校验：上级部门不能选择自己
- FR-004-009: 系统 MUST 在修改部门状态为停用时校验：不能有未停用的子部门、不能有已分配用户
- FR-004-010: 系统 MUST 在删除部门时校验：不能删除默认部门、不能有下级部门、不能有已分配用户、不能有已分配岗位
- FR-004-011: 系统 MUST 支持按部门名称模糊筛选部门列表
- FR-004-012: 系统 MUST 支持通过 @DataPermission 注解按 dept_id 过滤部门数据（数据权限基础）
- FR-004-013: 系统 MUST 提供 find_in_set 查询祖先中包含指定 deptId 的所有子部门（用于数据权限范围计算）
- FR-004-014: 系统 MUST 根据角色 ID 和部门树关联显示配置（deptCheckStrictly）查询角色关联的部门列表

## 4. 关键实体

| 实体 | 说明 | 关键属性 |
|------|------|----------|
| SysDept | 部门主表（自引用树） | deptId, parentId, deptName, orderNum, ancestors, status |

## 5. 验收场景

### 场景：新增子部门
- Given 管理员选中"总公司"节点
- When 点击新增 → 填写部门名称"研发部"、排序 1 → 提交
- Then 系统自动计算 ancestors 为"0,100"（100 为总公司 ID），部门创建成功

### 场景：修改上级部门时祖级列表自动更新
- Given 部门"测试组"当前 ancestors 为"0,100,200"
- When 将其上级部门从"研发部(200)"改为"产品部(300)"
- Then 系统自动将"测试组"及其子部门的 ancestors 更新为"0,100,300"

### 场景：不能删除包含用户的部门
- Given 部门"研发部"下有已分配用户
- When 管理员尝试删除该部门
- Then 系统返回"部门存在用户,不允许删除"

### 场景：编辑时排除自身及子部门
- Given 管理员编辑部门"研发部"（deptId=200）
- When 查询可选上级部门列表（/list/exclude/200）
- Then 返回的部门列表中不包含 deptId=200 及 ancestors 中包含"200"的部门

### 场景：停用有子部门的部门
- Given 部门"研发部"下有子部门"前端组"（状态正常）
- When 管理员将"研发部"状态改为停用
- Then 系统返回"该部门包含未停用的子部门!"

## 6. 非功能需求
- 部门查询 MUST 使用 @Cacheable 缓存，部门修改/删除 MUST 使用 @CacheEvict 清除缓存
- ancestors 字段 MUST 在新增和修改父部门时自动维护，格式为"0,parentId1,parentId2"（逗号分隔）
- 部门树的 children 字段为 @TableField(exist = false)，不持久化到数据库
- 所有写操作 MUST 使用 @RepeatSubmit 防重复提交

## 7. 依赖
- SysRole（角色管理）- 角色的数据权限配置依赖部门树
- SysUser（用户管理）- 用户关联部门，删除部门前需确认无用户关联
- SysPost（岗位管理）- 岗位关联部门，删除部门前需确认无岗位关联
